Vintage Story save format

How a .vcdbs save stores the world's blocks, from a database row down to a single block. The full text reference, with sources for every claim, is README.md.

verified with1.19.11.19.21.22.7

    1The save file

    A .vcdbs file is a plain SQLite database with five tables (plus SQLite's own sqlite_sequence):

    chunk mapchunk mapregion gamedata playerdata

    The world is cut into chunks: cubes of 32 × 32 × 32 blocks. Each chunk is one row of the chunk table, with two columns: position (where the cube is) and data (what's inside it). The tables store the world at three scales:

    • chunk is 3D (3.1). One row per cube, keyed by its x, z and y. The only table with blocks in it.
    • mapchunk is a 2D layer on top (3.2). One row per chunk column, the stack of chunks with the same x and z, keyed by just x and z. For each of its 32 × 32 block columns it keeps a few numbers, such as the height of the highest block rain can't fall through.
    • mapregion is coarser still (3.3). One row per 16 × 16 chunk columns, with world generation data.

    gamedata is a single row of world-wide data, such as block names and the clock (3.4). playerdata has one row per player (3.5).

    So a block column's map chunk gives its surface height, and that height names the one chunk holding the surface block. A top-down map only needs those chunks: about a fifth of the chunks in the test saves.

    Saves use SQLite's write-ahead log, so even read-only access creates -shm and -wal files next to the save. Read a copy, or open it with SQLite's immutable=1 option.

    Sources: table schema from 1.19 and 1.22.7 saves · SQLite: write-ahead log · table descriptions from the wiki · README §1

    2Common formats

    Formats used by more than one table.

    2.1Positions

    The position is a single 64-bit integer: the chunk's x and z in 21 bits each, its y (height) in 9, and its dimension in 10, split in two. These are chunk coordinates: multiply by 32 to get block coordinates. Dimension 0 is the world itself; others hold separate block spaces, such as the time-switched alternate world.

    y · 9 dim z · 21 bits dim x · 21 bits
    bit 63bit 0

    The grey bits are always 0, so positions are never negative. mapchunk and mapregion positions use the same packing with y = 0, a map region's x and z counting regions of 16 × 16 chunk columns.

    These coordinates are absolute. The game shows x and z from the world's centre instead, half the world's size in gamedata (3.4.2): in a default world of 1,024,000 × 1,024,000 blocks, block 512,000 is 0. It shows y as it is. That's checked against a player's position (3.5).

    Sources: wiki: VCDBS format · verified against 1.19 and 1.22.7 saves · README §2

    2.2Protobuf messages

    Every table's data column is a Protobuf message: like JSON where every key is a number and every value is raw bytes. Each field is its number and a wire type, then a varint, 4 or 8 bytes, or a length and that many bytes; a field can be another message. The names are the game's own, from a schema generated from its code.

    A list of numbers comes either way Protobuf allows: as the same field repeated, one value each, as in map chunks, or packed into one field of varints, as in map regions. A reader should take both. The messages aren't compressed; only a chunk's blocks, liquids and light are, inside their fields.

    Sources: every row of every table in the test saves parses · names from vs-proto's schema · lib/protobuf/ProtoBuf.zig · README §3

    2.3Tree attributes

    Some data isn't Protobuf but the game's own binary format, a tree attribute: a chunk's block entities (3.1.7) and the world's configuration (3.4.4). A tree is a list of entries, each a type byte, a string key and a value, ended by a single 0 byte. Numbers are little-endian, and strings are .NET BinaryWriter strings: a varint byte length, then UTF-8.

    idtypeencoding
    1inti32
    2longi64
    3doublef64
    4floatf32
    5stringstring
    6treenested tree, ends with 0
    7item stacku8 is-null; if 0: i32 class, i32 id, i32 stack size, tree
    8byte arrayu16 length, bytes
    9boolu8
    10–16arraysi32 count, then values: string, int, float, double, tree, long, bool

    3Tables

    3.1chunk

    One row per cube of 32 × 32 × 32 blocks: its position (2.1), and a message of its blocks, liquids, light and block entities.

    3.1.1Fields

    A chunk's message, ServerChunk, has these fields:

    #namestatus
    1blocksCompresseddecoded
    2lightCompressedlight, the planes
    3lightSatCompressedlight, the palette
    5EntitiesCountcount
    6EntitiesSerializedclass, version, data
    7BlockEntitiesCountcount
    8BlockEntitiesSerializeddecoded, see 3.1.7
    10lightPositionsunknown
    12GameVersionCreatedtext, e.g. "1.19.1"
    13EmptyBeforeSavebool
    14DecorsSerializednot decoded
    15savedCompressionVersion2
    16liquidsCompressedliquids, same as 1
    17BlocksPlacedcount
    18BlocksRemovedcount

    Field 1 holds the solid blocks, field 16 the liquids in the same format, and field 8 the block entities. Field 12 records the game version that created the chunk, so one save can mix versions. Not every field appears in every chunk.

    Light is a layer of the same kind as blocks, split across two fields: field 3 is the palette and field 2 the bit planes. Each light value packs sunlight in bits 0–4, 22 under open sky, and light from blocks such as torches in bits 5–9; bits 10–19 are set only where block light is, probably its colour. A column gets light when world generation reaches stage 4 (3.2); most of its lowest chunks store none, presumably being dark all through.

    Sources: every chunk of the 1.19 and 1.22.7 saves scanned · names from vs-proto's schema · wiki: Chunk Data Storage · README §3

    3.1.2Block data

    The first 4 bytes are a little-endian i32, length. Its sign says how the palette (3.1.3) is stored: negative means the palette is stored as-is, positive means it's compressed with zstd, and 0 means the chunk is empty. Everything after the palette is one zstd-compressed block of bit planes.

    palette
    bit planes

    Both examples are real chunks from one column (x 15995, z 15999) of a 1.19.1 save.

    Sources: verified against a 1.19 save · src/vs/Compression.zig · README §4

    3.1.3Palette

    Instead of storing a full block ID for all 32,768 blocks, a chunk keeps a short list of the block types it uses: the palette, a list of i32 block IDs. Each block then only stores its position in that list. Slot 0 is always air (ID 0).

    Positions are stored in bits, and b bits can count 2b different positions. So the palette is treated as if it had the next power of two of slots. Only the real entries are stored; the extra slots are never referenced, and a reader should treat them as air rather than read past the stored entries.

    air block type padding

    3.1.4Block order

    The cube is flattened into one long list, like reading a book: across a row (x), then the next row (z), then the next page (y). Every block gets a number n from 0 to 32,767.

    Bits for those blocks are packed 32 to a little-endian i32. Block n lives in i32 number n / 32 (rounded down), at bit n % 32 counting from the least significant bit. That works out neatly: each i32 holds one row of 32 blocks along x, and the bit index is the block's x.

    x 0 →→ 31
    z 0 ↓

    3.1.5Bit planes

    A block's palette position isn't stored as one number. With 3 bits per block, the chunk stores every block's first bit together (plane 0), then every block's second bit (plane 1), then every block's third bit (plane 2). To read a block, take its bit from each plane and add them up: plane 0 counts 1, plane 1 counts 2, plane 2 counts 4, and so on.

    The number of planes is log₂ of the rounded-up palette size, and each plane is 32,768 bits: 1,024 i32s, 4,096 bytes. The toy chunk below has 16 blocks.

    blocks n = 0–15

    palette

    stored as bit planes

    for comparison: bits side by side

    The format doesn't say why it uses planes, but they have clear advantages. When a chunk needs one more bit, a new plane of zeros is added and every existing bit stays where it is, while side-by-side packing would move every block's bits. Every block also sits at the same bit in every plane whatever the palette size. And planes tend to be long runs of the same bit, which zstd compresses well.

    Sources: verified against a 1.19 save · Chunk.getBlock in src/vs/Chunk.zig · README §4

    3.1.6Example: decoding a block

    A chunk from a 1.19.1 save containing a single placed block, start to finish.

    1. Find the chunk's row.

    2. Read field 1 (39 bytes). The first 4 bytes are f8 ff ff ff, which is −8: the palette is stored as-is and is 8 bytes long.

      palette = [ 0, 164 ] → 2 slots → 1 bit per block → 1 plane

    3. Decompress the remaining 27 bytes with zstd.

      27 bytes → 4,096 bytes = 1 plane × 1,024 i32s × 4 bytes

    4. Exactly one bit in the whole plane is set.

      i32 242, bit 5 → n = 242 × 32 + 5 = 7,749

    5. Turn n back into a position inside the chunk.

      x = n % 32 = 5 · z = ⌊n / 32⌋ % 32 = 18 · y = ⌊n / 1024⌋ = 7

    6. Look it up. The bit is 1, so the palette position is 1.

      palette[1] = 164, at world block (511,845, 135, 511,986)

    Source: chunk (15995, 4, 15999) of a 1.19.1 save

    3.1.7Block entities

    Blocks that need extra data, like chests, signs and chiseled blocks, have a block entity. Each one is a field 8 entry: the class name as a string, then a tree attribute (2.3).

    Every block entity starts with posx, posy, posz (absolute block coordinates) and blockCode. The most common classes in the sample 1.19 save are MicroBlock (8,343), Generic (4,364), BerryBush (632), GenericTypedContainer (370), Crate (274) and GroundStorage (184); the larger 1.22.7 world's ruins have most of the same, led by MicroBlock (40,528) and Generic (22,933). GroundStorage, items placed on the ground, keeps item stacks in its inventory; what their IDs refer to isn't decoded yet.

    Sources: every block entity of a 1.19 save (14,447) and of the 1.22.7 saves (77,462) parses · README §5

    3.1.8Chiseled blocks

    A chiseled block is an ordinary block in the chunk with a MicroBlock block entity holding its shape: a 16 × 16 × 16 voxel grid stored as a list of boxes (cuboids), plus materials, a list of block IDs from the same ID space as the palettes.

    Each box is one 32-bit number. Written in hexadecimal, every 4 bits are one digit, so the box reads off digit by digit: two digits of material (an index into materials), then the far corner, then the near corner, each as z, y, x. The far corner is stored minus 1, so a box reaching the edge fits in one digit (F = 15 means up to 16).

    box 1

    box 1, as stored

    boxhexxyzmaterial

    The block starts as a real chiseled block from the sample save, "Aged polished rock (Granite)": four boxes of one material. Each box has its own colour here; in the game all four are granite.

    Sources: all 20,407 boxes of a 1.19 save and 101,400 of a 1.22.7 save decode to boxes inside the block, with materials in the list · 1.22.7 code: vssurvivalmod BEMicroBlock.cs · README §5

    3.2mapchunk

    One row per chunk column, keyed by its x and z (2.1, y 0). Its message, ServerMapChunk, is 10 to 17 KB, and most of its fields are a value for each of the column's 1,024 block columns, at index z × 32 + x, written as one field each.

    #namecontents
    3RainHeightMapper block column: the height of the highest block rain can't fall through
    4currentpassthe world generation stage, below
    7WorldGenTerrainHeightMapper block column: the ground before plants and trees grew
    10YMaxthe highest block that isn't air
    13TopRockIdMapper block column: the block ID of the top rock layer
    16WorldGenVersionas gamedata's
    …fields 1, 8, 9, 11, 12, 15 and 17: mods' and the game's data by key, scheduled updates, new block entities, snow, cave shapes, and an unused map
    18newer than the schema; unknown

    The rain height falls through plants and loose stones but stops at water, so it's the ground, or a water surface. The game's own map draws it. A column with no blocks has 0, and a few hold 65,531 to 65,535: the game keeps these heights as unsigned 16-bit numbers, so those are −5 to −1. A row stays when its blocks are removed, so a reader should check the block at the height it gives.

    The terrain height is set by world generation and never changed afterwards. For seas and lakes, it's their bed.

    The stage is the column's next world generation pass (EnumWorldGenPass), not the last one done. Passes 2 to 5 need the columns around, so everything finished is ringed by partly generated columns, one ring per stage, each one chunk column wide. Only stage 6 is finished; at stages 2 and 3 there are no trees or plants yet.

    valuenext passgenerates
    1Terrainterrain, rock layers, caves
    2TerrainFeaturesdeposits, structures, ponds
    3Vegetationplants, shrubs, trees, rivulets
    4NeighbourSunLightFloodsnow, light across chunks
    5PreDonecreatures
    6Done–

    Sources: every row of the test saves parses; heights checked against the highest block of every column · names from vs-proto's schema and meanings from vsapi IMapChunk.cs · stages from the wiki: WorldGen Concept · README §7

    3.3mapregion

    One row per 16 × 16 chunk columns, 512 × 512 blocks, keyed by the region's x and z (2.1). Its message, ServerMapRegion, holds the maps world generation drew the region from. Each map is a square grid of numbers, packed, with a few rows and columns of padding copied from the regions around it so they blend at the edges; the grid inside the padding, its inner size, can be finer than one value per chunk column.

    #mapinner size
    1LandformMap32 × 32
    2ForestMap16 × 16
    3ClimateMap16 × 16
    4GeologicProvinceMap8 × 8
    5, 6BushMap, FlowerMap32 × 32, 16 × 16
    8OreMapsone per ore, by name: 31
    12RockStrataone per rock layer: 16, each 32 × 32
    15BeachMap32 × 32
    16BlockPatchMapsone per kind of patch, such as mushrooms
    17, 18UpheavelMap, OceanMap16 × 16

    Besides the maps, field 11 lists the structures world generation placed: lakes, ruins, villages, traders and more, each with a code such as small5.json/lakes and its box in absolute block coordinates, so a map could label them. Field 9 keeps the game's and mods' data by key, such as the weather.

    Sources: sizes and keys in every test save · names from vs-proto's schema · wiki: VCDBS format · README §8

    3.3.1Climate map

    The climate map, field 3, has a value every 32 blocks: 16 × 16 inside 2 cells of padding. Each value packs the climate there at sea level: temperature and rainfall, a byte each, 0 to 255. Between the values, the game interpolates.

    0 temperature rainfall other
    bit 31bit 0

    The top byte is always 0. The lowest isn't the climate: it's set in about 30% of the values in the test saves, and what it means isn't known. The test saves' temperatures are 84 to 139 and their rainfalls 4 to 255.

    Height changes both: it's colder higher up, by 1 for every 1.5 blocks above sea level, and the rainfall changes too. The game tints grass, leaves and water by the result, picking a colour from a climate colour map by temperature across and rainfall down. That's checked against the game's own map, whose water is that colour to within 1%.

    Sources: the grid's sizes in every test save · vsapi IntDataMap2D.cs and Climate.cs · blocks.md: climate and season tint · README §8

    3.4gamedata

    A single row holding one SaveGame message: block and item IDs, the world's size, clock and settings, and more.

    3.4.1Block and item IDs

    Palettes and chiseled blocks only hold numeric block IDs. The names are in field 11, a list of named entries: BlockIDs lists every ID with its block code, and ItemIDs does the same for items. A mod's codes carry its name, such as primitivesurvival:, and its IDs follow the game's.

    ID1.22.7 world1.19 sample
    0airair
    1mantlemantle
    164creativeblock-2creativeblock-12

    The same number means different blocks in different saves: 2966 is water-still-7 in the 1.22.7 world but a snowy fireclay roof corner in the 1.19 sample. So every save has to be read with its own list.

    Sources: every block ID in the test saves has a code · src/vs/GameData.zig · README §6

    3.4.2World size and sea level

    Fields 1, 2 and 3 are the world's size: 1,024,000 blocks east to west, 256 high and 1,024,000 north to south by default. The game shows positions from the middle, half of those across (2.1).

    The sea level isn't stored; the game derives it from the height: × 110 / 255, rounded down, so 110 in a default world. Water fills the blocks below it, so the top water block of a sea or lake is at y 109.

    Sources: sea level from the wiki, matching the water in the test saves · README §6

    3.4.3Date

    TotalGameSeconds, field 12, counts game time from 00:00 on 1 January of the first year, which the calendar numbers 1386. Divide by 3,600 for hours and by HoursPerDay, field 25, 24, for days; a year is 12 months of the world's daysPerMonth (3.4.4), 9 by default. Field 38 is the time the world was created.

    The 1.22.7 worlds were created at 3,139,200 seconds: 872 hours, so 36 days and 8 hours, which is 08:00 on 1 May 1386. A map coloured like the game's tints grass and leaves for the season on the save's date.

    Sources: the calendar from vsapi IGameCalendar.cs · README §6

    3.4.4World configuration

    Field 31 is the world's settings, chosen when it was created, as a tree attribute (2.3). The values are mostly strings, such as gameMode: "survival", startingClimate: "temperate", seasons: "enabled", daysPerMonth: "9" and spawnRadius: "5000", how far from the centre new players appear. A world with the colour-accurate map has colorAccurateWorldmap as the number 1.

    The row holds more besides: the world's name (13), its seed (7), the game versions that created it and last saved it (18, 21), and an identifier (34) that names the game's map cache (4).

    Sources: every world configuration in the test saves parses · README §6

    3.5playerdata

    One row per player who has joined, keyed by playeruid. Its message, ServerWorldPlayerData, holds their inventories, game mode, death count and player entity, which includes their position. Their privileges aren't in the save but in JSON files in the data folder's Playerdata.

    The message isn't decoded further, but a player's position can be found in it: the only run of three little-endian 64-bit floats inside the world, stored two or three times, the entity's x, y and z in absolute block coordinates.

    This position confirms how the game shows coordinates (2.1). One player stood on the ground where the game showed 409, 111, −304; that column's rain height (3.2) is 110, so their feet were at 111. After they flew up and moved a few blocks, the save held them at 512,409.0, 193.9, 511,699.3: x 512,409 − 512,000 = 409, and z −300.7.

    Sources: table description from the wiki: VCDBS format · the position found in the 1.22.7 saves · README §2

    4Drawing a top-down map

    A simple map needs only the top block of each column. Scan each column down from the top until something isn't air, and colour the pixel by that height. Columns with no blocks at all stay black. Click cells in the side view to add or remove blocks.

    map, one pixel per column

    side view

    The game's own world map works the same way, with refinements: it takes each column's height from the stored rain height (3.2) instead of scanning, reads liquids too (they live in field 16, not field 1), looks under snow, colours by a per-block map colour, and shades slopes by comparing each column with its neighbours. It only draws finished columns, at stage 6. Its colour-accurate mode colours each block by its texture instead, tinted by the climate (3.3.1) and the season on the save's date (3.4.3).

    That map isn't in the save. Each player's game keeps what it has drawn in the data folder, in Maps/<id>.db, where <id> is gamedata's identifier (3.4.4): another SQLite database whose mappiece table has a row per chunk column, keyed like map chunks, holding its 32 × 32 pixels, red in the lowest byte, at index z × 32 + x. It only has what that player has seen, so a map of a whole world, or one made on a server, is drawn from the save, and the cache is a way to check it.

    Sources: 1.22.7 code, vsessentialsmod ChunkMapLayer.cs · the map cache decoded and compared with Storymap's maps of 1.22.7 worlds · README §7

    5Open questions

    • The other fields. Entities' data (6), field 10, the empty flag (13), decor (14) and the colour of light.
    • The other tables. The schema names every field, but playerdata hasn't been decoded beyond the player's position, nor have the values of mapregion's maps other than the climate's, the climate's lowest byte, or a few fields newer than the schema.
    • Other dimensions. No test save has chunks outside dimension 0.
    • Mods. Modded block and item codes carry their mod's domain, such as primitivesurvival:; which generated structures come from a mod isn't known.
