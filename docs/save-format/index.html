Vintage Story save format

How a .vcdbs save stores the world's blocks, from a database row down to a single block. The full text reference, with sources for every claim, is README.md.

verified with1.19.11.19.21.22.7

01The save is an SQLite database

A .vcdbs file is a plain SQLite database with five tables (plus SQLite's own sqlite_sequence):

chunk mapchunk mapregion gamedata playerdata

The world is cut into chunks: cubes of 32 × 32 × 32 blocks. Each chunk is one row of the chunk table, with two columns: position (where the cube is) and data (what's inside it). mapchunk has one row per column of chunks, and mapregion one per 16 × 16 columns.

Saves use SQLite's write-ahead log, so even read-only access creates -shm and -wal files next to the save. Read a copy, or open it with SQLite's immutable=1 option.

Sources: table schema from 1.19 and 1.22.7 saves · SQLite: write-ahead log · table descriptions from the wiki · README §1

02position packs three numbers into one

The position is a single 64-bit integer. The lowest 27 bits are the chunk's x, the next 27 its z, and the top 10 its y (height). These are chunk coordinates: multiply by 32 to get block coordinates.

y · 10 z · 27 bits x · 27 bits
bit 63bit 0

SQLite integers are signed, so a chunk with y ≥ 512 (top bit set) is stored as a negative number. mapchunk positions use the same packing with y = 0.

Sources: verified against a 1.19 save · src/Chunk.zig · README §2

04Inside field 1: three parts

The first 4 bytes are a little-endian i32, length. Its sign says how the palette (next section) is stored: negative means the palette is stored as-is, positive means it's compressed with zstd, and 0 means the chunk is empty. Everything after the palette is one zstd-compressed block of bit planes.

05The palette, rounded up to a power of two

Instead of storing a full block ID for all 32,768 blocks, a chunk keeps a short list of the block types it uses: the palette, a list of i32 block IDs. Each block then only stores its position in that list. Slot 0 is always air (ID 0).

Positions are stored in bits, and b bits can count 2b different positions. So the palette is treated as if it had the next power of two of slots. Only the real entries are stored; the extra slots are never referenced, and a reader should treat them as air rather than read past the stored entries.

air block type padding

06Numbering the 32,768 blocks

The cube is flattened into one long list, like reading a book: across a row (x), then the next row (z), then the next page (y). Every block gets a number n from 0 to 32,767.

Bits for those blocks are packed 32 to a little-endian i32. Block n lives in i32 number n / 32 (rounded down), at bit n % 32 counting from the least significant bit. That works out neatly: each i32 holds one row of 32 blocks along x, and the bit index is the block's x.

z 0 ↓

07Bit planes

A block's palette position isn't stored as one number. With 3 bits per block, the chunk stores every block's first bit together (plane 0), then every block's second bit (plane 1), then every block's third bit (plane 2). To read a block, take its bit from each plane and add them up: plane 0 counts 1, plane 1 counts 2, plane 2 counts 4, and so on.

The number of planes is log₂ of the rounded-up palette size, and each plane is 32,768 bits: 1,024 i32s, 4,096 bytes. The toy chunk below has 16 blocks.

The format doesn't say why it uses planes, but they have clear advantages. When a chunk needs one more bit, a new plane of zeros is added and every existing bit stays where it is, while side-by-side packing would move every block's bits. Every block also sits at the same bit in every plane whatever the palette size. And planes tend to be long runs of the same bit, which zstd compresses well.

Sources: verified against a 1.19 save · Chunk.getBlock in src/Chunk.zig · README §4

08A real block, decoded

A chunk from a 1.19.1 save containing a single placed block, start to finish.

  1. Find the chunk's row.

  2. Read field 1 (39 bytes). The first 4 bytes are f8 ff ff ff, which is −8: the palette is stored as-is and is 8 bytes long.

    palette = [ 0, 164 ] → 2 slots → 1 bit per block → 1 plane

  3. Decompress the remaining 27 bytes with zstd.

    27 bytes → 4,096 bytes = 1 plane × 1,024 i32s × 4 bytes

  4. Exactly one bit in the whole plane is set.

    i32 242, bit 5 → n = 242 × 32 + 5 = 7,749

  5. Turn n back into a position inside the chunk.

    x = n % 32 = 5 · z = ⌊n / 32⌋ % 32 = 18 · y = ⌊n / 1024⌋ = 7

  6. Look it up. The bit is 1, so the palette position is 1.

    palette[1] = 164, at world block (511,845, 135, 511,986)

Source: chunk (15995, 4, 15999) of a 1.19.1 save

09Block entities

Blocks that need extra data, like chests, signs and chiseled blocks, have a block entity. Each one is a field 8 entry: the class name as a string, then a tree attribute. Strings are .NET BinaryWriter strings: a varint byte length, then UTF-8.

A tree is a list of entries, each a type byte, a string key and a value, ended by a single 0 byte:

idtypeencoding
1inti32
2longi64
3doublef64
4floatf32
5stringstring
6treenested tree, ends with 0
7item stacku8 is-null; if 0: i32 class, i32 id, i32 stack size, tree
8byte arrayu16 length, bytes
9boolu8
10–16arraysi32 count, then values: string, int, float, double, tree, long, bool

Every block entity starts with posx, posy, posz (absolute block coordinates) and blockCode. The most common classes in the sample 1.19 save are MicroBlock (8,343), Generic (4,364), BerryBush (632), GenericTypedContainer (370), Crate (274) and GroundStorage (184).

Chiseled blocks

A chiseled block is an ordinary block in the chunk with a MicroBlock block entity holding its shape: a 16 × 16 × 16 voxel grid stored as a list of boxes (cuboids), plus materials, a list of block IDs from the same ID space as the palettes. Each box is one 32-bit number:

10Block names: the gamedata table

Palettes and chiseled blocks only hold numeric block IDs. The names are in the save's single gamedata row, another Protobuf message. One of its entries, BlockIDs, lists every ID with its block code; ItemIDs does the same for items.

ID1.22.7 world1.19 sample
0airair
1mantlemantle
164creativeblock-2creativeblock-12

The same number means different blocks in different saves: 2966 is water-still-7 in the 1.22.7 world but a snowy fireclay roof corner in the 1.19 sample. So every save has to be read with its own list. The same row also holds the world's settings, such as how far from the centre new players spawn.

It also holds the world's height, 256 blocks by default, but not its sea level. The game derives that: the height × 110 / 255, rounded down, so 110 in a default world. Water fills the blocks below it, so the top water block of a sea or lake is at y 109.

Sources: every block ID in both saves has a code · src/GameData.zig · sea level from the wiki, matching the water in both saves · README §6

11Using it: a top-down map

A simple map needs only the top block of each column. Scan each column down from the top until something isn't air, and colour the pixel by that height. Columns with no blocks at all stay black. Click cells in the side view to add or remove blocks.

map, one pixel per column

side view

The game's own world map works the same way, with refinements: it takes each column's height from a stored rain height map instead of scanning, reads liquids too (they live in field 16, not field 1), looks under snow, colours by a per-block map colour, and shades slopes by comparing each column with its neighbours.

Source: 1.22.7 code, vsessentialsmod ChunkMapLayer.cs

12Still unknown

  • The other fields. Light (2, 3), entities (5, 6), field 10, decor (14) and the small number fields.
  • The other tables. mapregion and playerdata haven't been decoded, and mapchunk only its height maps; of gamedata, only the ID lists, world size and world settings have.
  • In-game coordinates. The game shows coordinates shifted from these absolute ones; the exact offset hasn't been confirmed.
  • Chiseled blocks and ground storage on 1.22. The 1.22.7 test world has neither yet.
  • Mods. Whether modded block codes carry a domain prefix, in palettes and gamedata, hasn't been checked.
