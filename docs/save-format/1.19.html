Vintage Story save format

How a .vcdbs save stores the world's blocks, from a database row down to a single block.

verified with1.19.11.19.2

01The save is an SQLite database

A .vcdbs file is a plain SQLite database with five tables (plus SQLite's own sqlite_sequence):

chunk mapchunk mapregion gamedata playerdata

The world is cut into chunks: cubes of 32 × 32 × 32 blocks. Each chunk is one row of the chunk table, with two columns: position (where the cube is) and data (what's inside it).

02position packs three numbers into one

The position is a single 64-bit integer. The lowest 27 bits are the chunk's x, the next 27 its z, and the top 10 its y (height). These are chunk coordinates: multiply by 32 to get block coordinates.

y · 10 z · 27 bits x · 27 bits
bit 63bit 0

SQLite integers are signed, so a chunk with y ≥ 512 (top bit set) is stored as a negative number.

03data is a list of numbered fields

The data blob is a Protobuf message: like JSON where every key is a number and every value is raw bytes. Names are best guesses unless the field is marked decoded.

Field 1 holds the solid blocks. Field 12 records the game version that last wrote the chunk, so one save can mix versions.

04Inside field 1: three parts

The first 4 bytes are a little-endian i32, length. Its sign says how the palette (next section) is stored: negative means the palette is stored as-is, positive means it's compressed with zstd, and 0 means the chunk is empty. Everything after the palette is one zstd-compressed block of bit planes.

05The palette, rounded up to a power of two

Instead of storing a full block ID for all 32,768 blocks, a chunk keeps a short list of the block types it uses: the palette, a list of i32 block IDs. Each block then only stores its position in that list. Slot 0 is always air (ID 0).

Positions are stored in bits, and b bits can count 2b different positions. So the palette is treated as if it had the next power of two of slots. Only the real entries are stored; the extra slots are never referenced, and a reader should treat them as air rather than read past the stored entries.

06Numbering the 32,768 blocks

The cube is flattened into one long list, like reading a book: across a row (x), then the next row (z), then the next page (y). Every block gets a number n from 0 to 32,767.

Bits for those blocks are packed 32 to a little-endian i32. Block n lives in i32 number n / 32 (rounded down), at bit n % 32 counting from the least significant bit. That works out neatly: each i32 holds one row of 32 blocks along x, and the bit index is the block's x.

z 0 ↓

07Bit planes

A block's palette position isn't stored as one number. With 3 bits per block, the chunk stores every block's first bit together (plane 0), then every block's second bit (plane 1), then every block's third bit (plane 2). To read a block, take its bit from each plane and add them up: plane 0 counts 1, plane 1 counts 2, plane 2 counts 4, and so on.

The number of planes is log₂ of the rounded-up palette size, and each plane is 32,768 bits: 1,024 i32s, 4,096 bytes. The toy chunk below has 16 blocks.

The format doesn't say why it uses planes, but they have clear advantages. When a chunk needs one more bit, a new plane of zeros is added and every existing bit stays where it is, while side-by-side packing would move every block's bits. Every block also sits at the same bit in every plane whatever the palette size. And planes tend to be long runs of the same bit, which zstd compresses well.

08A real block, decoded

A chunk from a 1.19.1 save containing a single placed block, start to finish.

  1. Find the chunk's row.

  2. Read field 1 (39 bytes). The first 4 bytes are f8 ff ff ff, which is −8: the palette is stored as-is and is 8 bytes long.

    palette = [ 0, 164 ] → 2 slots → 1 bit per block → 1 plane

  3. Decompress the remaining 27 bytes with zstd.

    27 bytes → 4,096 bytes = 1 plane × 1,024 i32s × 4 bytes

  4. Exactly one bit in the whole plane is set.

    i32 242, bit 5 → n = 242 × 32 + 5 = 7,749

  5. Turn n back into a position inside the chunk.

    x = n % 32 = 5 · z = ⌊n / 32⌋ % 32 = 18 · y = ⌊n / 1024⌋ = 7

  6. Look it up. The bit is 1, so the palette position is 1.

    palette[1] = 164, at world block (511,845, 135, 511,986)

09Using it: a top-down map

A simple map needs only the top block of each column. Scan each column down from the top until something isn't air, and colour the pixel by that height. Columns with no blocks at all stay black. Click cells in the side view to add or remove blocks.

10Still unknown

  • Block names. Palettes hold numeric IDs like 6769. The mapping to block codes is likely in gamedata.
  • The other fields. Light (2, 3), entities (6), decor (14) and the rest aren't decoded. Block entities (8) are only partly read.
  • In-game coordinates. The game shows coordinates shifted from these absolute ones; the exact offset hasn't been confirmed.
  • The other tables. mapchunk, mapregion, gamedata and playerdata haven't been decoded.
